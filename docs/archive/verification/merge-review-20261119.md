## 优先修正的计算与可靠性问题

### 1. DDB 折算因子缺失可能生成假净申购（高优先级）

位置：`etf_backend/sources.py:DDBAdapter.collect_history`、`etf_backend/model.py:fund_flows`。

DDB NAV 行写成 `[day, NAV, 1.0]`，而共同公式要求 NAV 调整因子变化验证折算比。单独传入 SPLIT_RATIO 不保证其被采用。

离线合成验证：上一日份额 1 亿、NAV=10；当天仅发生 1.1 倍份额折算，份额 1.1 亿、NAV=10/1.1。真实净申赎应为 0。恒定因子 1 的输入得到 **+0.909090909 亿元**；把当天有效因子设为 1.1 后结果为 0。此为合成反例，未证明生产上存在该笔误报。

建议：依据 DDB 字段定义补充可验证的调整因子/公司行为证据；无法验证时标记缺口，不能默认“无折算”。实现 NET_INFLOW 独立对账，但不能未经验证直接以该字段替代共同公式。验收覆盖大小比例折算、分红、上市首日和缺失 NAV。

### 2. DDB 就绪日期使用自然日，且行情覆盖只查全局 MAX（高优先级）

位置：`etf_backend/collect.py:main`、`etf_backend/sources.py:DDBAdapter.status`。

采集前目标为 `min(end, today-1自然日)`。周一取到周日，或 end 为假日时，完整的上一交易日数据仍可能被拒绝。合成会话中，同一批周五 2026-11-13 数据：目标为周五时 ready=true，目标为周日 11-15 时 ready=false。目标应先由交易日历和发布策略确定。

份额检查逐只 MAX 日期，但行情只查篮子全局 MAX：一只标的有新行情即可满足日期条件，其他标的漏数未必在就绪检查中被发现。份额日期达标也未验证最新值是否为空或有效。

建议：逐只检查目标交易日价格/成交额、份额、净值的有效性；市场能力与份额能力分开报告。验收覆盖周末、长假、一只落后、一只缺 NAV、全源陈旧。

### 3. 实时 ready 状态的缓存没有跟踪实时文件（中优先级）

位置：`etf_backend/web.py:source_status`。

缓存键只包含日期与日频 seed 文件版本，但结果包含实时缓存的 ready。离线验证：第一次查询时盘中缓存不存在，ready=false；随后写入有效缓存、日频 seed 不变，ready 仍为 false。反向失效和跨日新鲜度也需覆盖。实际 `/api/live` 单独读缓存，故来源状态与行情接口可能不一致。

建议：只缓存日频状态，实时状态每次独立轻量检查；或把实时文件版本及必要的新鲜度边界加入键。网页日频 ready 的 expected 来自现存快照日期，双源同时陈旧时亦不能独立发现落后于真实交易日。

### 4. 旧成交量输入/归档仍可按成交额解释（高优先级）

位置：`etf_backend/collect.py:main --burst-input`、`etf_backend/burst.py:BurstDay.payload`、`src/assets/radar.js`。

离线导入只读取四列数值，不校验 metric/unit；检测器输出固定 `metric=turnover`。前端仍允许 `signal.amount ?? signal.volume` 并显示为亿元。旧 volume 文件被导入或展示时可能产生单位错标。仅有比值无量纲，并不能保证单位安全或阈值效果等价。

建议：新归档/导出要求 `schema_version、metric、unit、rule_version、basket_hash、baseline_as_of`，不兼容时拒绝或明确按历史版本展示。禁止把旧成交量事件覆盖成成交额事件，分别保留、回放、验收。

### 5. 更新脚本可能掩盖子进程失败（中优先级）

位置：`scripts/update-sources.ps1:Invoke-History` 与 crowding 调用。

该脚本依靠 try/catch 统计失败，但没有在每次调用后检查 `$LASTEXITCODE`。被调用的 `python-backend.ps1` 以 `exit $LASTEXITCODE` 返回；Windows PowerShell 的非零退出码不等于抛出异常，最后可能仍退出 0。`update-daily-all.ps1` 已有显式检查，可沿用相同做法。

建议：每步检查退出码；可选 DDB 失败记为降级但不能覆盖 RQData 失败状态。用不访问网络的替身脚本验证必需源失败返回非零、后续独立模块继续、可选源失败明确记录。

## 阈值与计算口径建议

1. **成交额主指标可以保留，必须重新校准。** 同窗 `R=A_k/max(Pq20_k,Pq60_k)`，全天占比 `D=A_k/max(Median20_daily,Median60_daily)`。价格趋势会影响跨日成交额，和成交量阈值不完全等价。建议并行记录量与额，按 ETF、早盘/午后/尾盘比较独立验证集中的事件数、重点事件召回及首报延迟，再决定是否调整 5 倍、4%/12%/20%。
2. **显式展示有效样本数。** 当前基准允许近 20 日至少 19 个、近 60 日至少 55 个样本；窗口和全天样本独立筛选。把样本数、分位算法、缺失原因和参数版本写入归档。P75 是统计筛选参数，不等于已校准误报概率。
3. **区分早期候选和完整分钟确认。** 当前主信号由已结束 bar 驱动，收到 tick 主要用于证据补充，不能据此承诺秒级放量报警。若需更早提醒，可另做 tick 累计成交额增量的秒级候选，按相同秒进度比较基准；完整分钟规则维持正式确认，记录数据时延、检测时延和通知时延。
4. **行业分类周缓存属于近似。** 日度成分与周内首日行业标签组合，可能漏掉周内分类变化。长期复盘应支持按生效日的历史行业映射，或明确缓存近似和申万版本；不得将当前近似直接称为严格历史行业口径。
5. **不把信号等同交易主体。** 放量、溢价、指数联动与盘口可形成疑似集中交易证据；国家队身份仍需公开披露等独立信息。

## 性能实测与优化顺序

本机既有 `.local/python-backend/Scripts/python.exe`，20 只 ETF、60 个历史交易日、每日 240 个分钟点的常量合成样本；3 次基准生成中位耗时 **3.18 秒**，单日回放（含重新生成基准）**3.42 秒**。样本无事件。测量不含取数、tick 接收、文件发布、浏览器渲染或生产负载，不能外推告警时延。

| 顺序 | 建议 | 原因与验收 |
|---|---|---|
| 先做 | 按日缓存分钟基准，键含指标、参数、篮子和数据版本 | 启动/重连当前会重取近 60 日分钟；优先减少网络和重复构建。用冷/热启动耗时、API 调用数及结果一致性验收 |
| 再做 | 分离分钟看板发布和 tick 证据发布 | `PushSession.flush` 在有消息时约每秒重建快照并写文件，即使完整分钟不变；按内容版本发布，证据按需更新，降低 JSON/磁盘开销 |
| 再做 | 合并重复 tick、监控队列积压 | 当前队列上限 20000，入队可能阻塞 5 秒；对可替代 tick 保留最新值，完整 bar 不随意丢弃。测 queue depth、行情时间滞后与断线补齐情况 |
| 再做 | 日频 board 按版本返回，支持 ETag/304 或分块读取 | 当前 `/api/board` 每次序列化整个 seed；在多人访问下按首屏/历史区间拆分，测响应大小、P95 延迟和请求数 |
| 数据变大后 | DDB 批量 DataFrame 转换、减少 iterrows；窗口和使用前缀和 | 当前 Python 循环可优化，但先测 ETL 时间和 CPU 占比。保持缺分钟、午休和竞价边界一致，不为 20 只标的提前引入复杂基础设施 |

建议先修复单位版本、DDB 折算和日期/覆盖边界，再做基准缓存与发布去重。暂不建议为现有规模引入分布式队列或整体重写前后端。
